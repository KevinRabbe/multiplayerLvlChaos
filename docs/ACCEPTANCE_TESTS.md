# Acceptance Tests 1.0

A feature is not complete because code exists. This document defines the intended observable behavior.

## Primary reference session

Core social validation uses:

- 10 players;
- one 15-minute Morning Shift;
- normal quest generation;
- normal customer schedule;
- proximity communication enabled;
- no developer coaching players to accuse, lie, sabotage, use PA socially, or “be funny.”

Controls/rules may be explained. Emergent social strategy must not be prompted.

## Highest-level product test

> **Do players spontaneously talk about what other players are doing?**

Examples of success:

- “Why are you doing that?”
- “Who moved these?”
- “Was that you?”
- “Stop touching my cans.”
- “I was fixing it.”
- “He did it.” / “No I didn't.”

If 10 players mostly perform silent independent checklists, the core product is not yet working even if all mechanics function technically.

## Social-interaction diagnostic targets

Across a normal 10-player match, initial healthy targets:

| Observation | Diagnostic target |
|---|---:|
| Players in at least one spontaneous gameplay conversation | ≥8/10 |
| Distinct accusation/defense exchanges | ≥3 |
| Visible quest-related conflicts | ≥2 |
| Voluntary cooperation moments | ≥2 |
| “what/why are you doing?” style interactions | ≥5 |
| Incidents causing verbal reaction/investigation | ≥50% |
| Major physical scene discovered after the fact | ≥1 often |
| Social PA use | desirable, not mandatory every round |

These are diagnostic rather than score targets; do not mechanize behavior to hit them.

## Genuine uncertainty

Players should occasionally confidently reach the wrong conclusion about responsibility because they observed only part of a real event.

Good: several players blame Sarah while Alex actually caused the original event, with no false evidence generated by the game.

Bad A: everyone always knows exactly who caused everything → too much information.

Bad B: nobody can form any plausible theory → too little information/readability.

Multi-causal situations where several players independently contribute to one incident are especially valuable.

## Conversation must not depend entirely on incidents

Players should also react to directly observed behavior: plant carrying, repeated coffee drinking, can towers, ragdoll dragging, strange object movement, etc.

If nearly all social interaction happens only after corporate banners, physical world/state readability needs improvement.

## Quest-understanding standard

First-time player should understand what an assigned quest **requires** from title + condition text without developer clarification.

Target: ≥90% correct broad understanding.

Questions about strategy/other players are gameplay, not wording failures.

## Quest completion distribution

After players understand the game, target average roughly **1.5–2.1 completed quests/player** across multiple matches.

Healthy distribution includes some 3/3, many 1/3–2/3, occasional 0/3.

If near 2.9 average → probably trivial. If ~0.4 → probably too difficult/fragile.

## Heavy-quest standard

A Heavy quest should feel like a shift-long project that generates interaction, physical challenge, or public suspicious behavior. It must not become repetitive solitary busywork.

No normal authored quest should routinely require >~3 continuous minutes isolated from everyone else as the intended/optimal solution.

## Conflict-pair standard

Intentional soft conflicts should cause owners to notice that someone is changing/undoing the relevant world state.

They do not need to identify the exact opposing quest.

If both sides routinely complete without noticing each other, the pairing is socially weak.

If one interaction makes the exact quest ID obvious every time, behavior is too predictable.

## Shared-objective pressure

Experienced normal groups should initially reach 20 served in roughly **50–75%** of ordinary matches across a meaningful sample.

The objective should sometimes make several players abandon personal nonsense temporarily to stabilize checkout/store operation, then return to private behavior.

Failure modes:

- target always trivial while ignored → pressure too weak;
- organized groups must cashier constantly → pressure too strong.

## Opening phase

By end of first match, first-time players should broadly understand stocking, carts, checkout activation, and ~03:00 opening.

Subsequent rounds should usually have several players actually preparing rather than waiting idly for forced opening.

## Customer technical acceptance

| Test | Requirement |
|---|---|
| Permanent navigation bug/stuck | <2% and trending to effectively zero |
| Ordinary obstruction resolution | usually within ~10 sec |
| Customer eventually completes or intentionally abandons | ≥98% |
| Missing product hard-softlock | never |
| Active-customer ceiling | never exceeded |
| Checkout migration after lane failure | reliable |
| Indefinite confused state | never |

Customer behavior should be readable as broadly Normal / Impatient / Angry / Leaving without showing patience numbers.

Customers must support player interaction rather than become the main attraction.

## Physics interaction acceptance

| Action | Pass condition |
|---|---|
| Pick up small item | reliable on first reasonable attempt |
| Place product on shelf | predictable |
| Drop vs throw | distinct/predictable |
| Throw | direction/range understandable |
| Push cart slowly | controllable |
| Cart cargo | generally stays in during normal movement |
| Tip cart | cargo visibly spills |
| Carry medium object through doorway | awkward but possible |
| Cart onto roof | physically achievable |
| Stack cans | genuinely possible |
| Grab ragdolled player | understandable |
| Exit cart | always possible |

Awkward because of physics is good. Unreliable because control semantics are inconsistent is bad.

## Can-stack benchmark

Experienced tester must be able to construct stable **6-can stack/structure** without excessive fighting of the physics.

10-can arrangement should be difficult but feasible.

If 6 cans routinely explode/jitter apart, stacking quests are invalid until physics/interaction is fixed.

## Shopping-cart benchmark

Pass when:

- slow pushing predictable;
- steering degrades at speed;
- rider stable under normal motion;
- severe tip/impact can eject rider;
- cargo spills physically;
- impacts can cause agreed stumble/ragdoll;
- no routine orbital/infinite-velocity behavior;
- network correction under ~100 ms does not make it unusable.

## Physics stress target

Stress scene/match with approximately:

- 100 active moving rigid bodies;
- 10 players;
- up to 12 customers.

Must remain playable without persistent explosive jitter, authority collapse, or interaction becoming unusable.

## Ragdoll acceptance

- normal recovery ~1.5–2.5 sec;
- never permanently stuck;
- voice remains available conceptually;
- no unavoidable knockdown loop;
- recovery does not place player through geometry;
- dragging works only during ragdoll;
- drag releases on recovery.

## Mess persistence/environmental storytelling

By 15:00 a normal chaotic shift should visibly differ from 00:00.

Expected possible signs: displaced products, moved/tipped carts, open doors, empty containers, puddles, delivery boxes, moved chairs, object piles.

If world remains pristine every round → persistence/pressure too weak.

If world becomes functionally unusable by ~05:00 every round → chaos pressure too high.

A valuable recurring observation is a player discovering a scene they did not witness and saying the equivalent of “what happened here?”

## Map density/traversal

On sales floor, player should rarely go >~20–30 sec without seeing/hearing another employee unless deliberately avoiding them.

Storage/roof may create longer isolation.

Stopwatch targets:

- ManagerOffice→Entrance sprint ~6–8 sec.
- Storage→Produce ~6–8 sec.
- Longest reasonable indoor route ≤10 sec.

Different areas should have different evidence quality: entrance/checkouts public, office partially visible, storage/roof private.

## Voice geography

Human experience target:

- same aisle: easy conversation;
- adjacent aisle: often audible/partially obscured;
- several aisles away: generally not clearly understandable;
- Storage↔Checkout: ordinary speech not clear;
- behind closed staff-room door: noticeably muffled;
- Roof↔indoor sales floor: generally isolated;
- PA: intelligible globally.

Players should occasionally overhear nearby conversations not addressed to them.

## PA acceptance

Within early sessions players should spontaneously understand/use PA for global social purposes (warning, accusation, request, joke, coordination) without being instructed to do so.

Do not add cooldown solely because PA can be annoying. Add restrictions only if repeated tests show one player can make the match miserable and physical contestability/mute are insufficient.

## Incident frequency/social value

Average target around 3/match; acceptable normal range 1–5.

For each incident record whether players:

- verbally reacted;
- investigated;
- cooperated;
- suspected/accused;
- used PA.

Incident must clearly communicate the problem while preserving uncertainty about cause.

## Character recognition/readability

After ~2–3 same-lobby rounds, players should begin recognizing several recurring employees visually without relying only on nameplates; informal target perhaps 4–6 of the other nine.

At ~6–8 m observers should broadly distinguish:

- normal vs very drunk;
- normal vs highly caffeinated;
- normal vs extremely stuffed.

Do not solve weak visual state with HUD icons.

Across a 10-player lobby, several characters should be ordinary, several distinctive, and roughly one may be immediately ridiculous. Contrast matters.

## Onboarding

With intended short onboarding and no developer coaching, within first real shift ≥80% of first-time players should understand how to:

- move/camera;
- grab/drop;
- throw;
- push cart;
- use/interact;
- view private quests;
- identify shared served-customer objective.

By second shift controls should not be the primary confusion source.

Do **not** test whether tutorial teaches deception; it deliberately should not.

## Results/recontextualization

A healthy shift often produces at least one reaction equivalent to:

- “THAT'S why you were doing that.”
- “The carts actually were your quest?”

Results must remain short enough to encourage rematch: full default presentation ~60–90 sec max and accelerable.

## Same-lobby continuity

By round 2–3, players should naturally reference previous rounds/reputations (“don't let him near carts again”, “this time it isn't my quest”).

No persistent reputation score should be needed.

## Replayability

Primary prototype question is not whether one shift was fun, but whether players voluntarily want another shift on the exact same map.

Repeated same-group sessions are more informative than many one-off single rounds.

## Failure-reason classification for quests

For every failed quest in internal testing classify:

- player chose not to pursue → fine;
- another player interfered → usually healthy;
- shared emergency took priority → healthy;
- time ran out → often fine;
- finite resource consumed/destroyed → potentially fine;
- requirement misunderstood → wording/UI problem;
- obvious success not detected → serious validator bug;
- physics made reasonable solution impossible → physics/design bug;
- impossible at assignment → generator bug;
- required system failed → serious implementation bug.

## “The game believed me” requirement

When a reasonable human observer would say a quest clearly succeeded, the authoritative validator should almost always agree. Invisible boundary/pedantic-condition failures are high-priority bugs.

## Fail-soft stress test

Deliberately:

- block entrance;
- turn all checkouts off;
- tip carts;
- scatter products/delivery;
- obstruct aisles;
- break glass;
- create/ignore puddles;
- fall off roof.

Objectives/customers may fail/complain, but the match itself must continue without requiring restart.

## Lost Property test

Launch several objects OOB, including unique intact props.

Expected:

- after ~5 sec recover exactly once;
- safe LostProperty placement;
- no duplicate/invisible original ownership;
- intact unique objects recover;
- destroyed unique objects do not resurrect.

## Player-count tests

### Six-player public minimum

Game remains functional though quieter. Conflict generation scales down. Same 20 shared target is tested initially before deciding dynamic scaling.

If six feels fundamentally empty, reconsider public minimum rather than redesigning whole game around low population.

### Two-player private

Not a social-balance target. Requirements: match runs, impossible social quests not assigned, customers/shared systems function, sensible private quest set generated.

## Quest-generator simulation

Across at least 100,000 generated 10-player rounds in automated/dev tests:

- zero impossible-at-assignment sets;
- no resource-budget violation;
- exactly 3/player;
- max one Heavy/player;
- prep/delivery limits respected;
- conflict range reasonable;
- repeat avoidance works where alternatives exist.

Report quest frequencies/resource utilization/conflict distribution to detect bias.

## No tester coaching

Do not tell players to:

- accuse;
- lie;
- sabotage;
- use PA socially;
- “be funny.”

If those behaviors require coaching, the design has not yet produced them naturally.

## Observer match sheet

Record at minimum:

- player count / first-time vs experienced;
- served-customer result;
- quest completions/player;
- incidents fired;
- approximate accusation count;
- cooperation moments;
- observed quest conflicts;
- PA uses;
- major physics/network failures;
- NPC failures;
- recontextualization moments;
- one-sentence biggest spontaneous story;
- number wanting immediate rematch.

The one-sentence spontaneous story is particularly valuable.

## Prototype success threshold

Do not declare the concept successful after one lucky round.

Target at least **5 proper 8–10-player sessions**, with repeat rounds, showing the same structural pattern across groups:

- private motives;
- overlapping consequences;
- partial observations/theories;
- player-to-player interpretation;
- cooperation/interference;
- reveal recontextualization;
- desire for another round.

## Red flags requiring design work

- players mostly silent;
- everyone plays alone;
- exact quest IDs instantly obvious;
- nobody can form plausible causality theories;
- incidents ignored/spammy;
- global-like voice destroys locality;
- map feels empty/too large;
- shared objective trivial or dominates entire match;
- quests complete passively/automatically;
- quest validation frequently rejects obvious success;
- players blame controls rather than understandable interference;
- world pristine at end or unusable extremely early;
- results reveal causes no recontextualization;
- players immediately want a different map rather than rematch.

## Green flags

Especially valuable spontaneous feedback:

- “I genuinely thought he did it.”
- “I was fixing it and everybody blamed me.”
- “I didn't know why she kept taking the watermelons until results.”
- “We spent five minutes fighting over the freezer.”
- “I walked into the office and had no idea what happened.”
- “I lied about my quest because otherwise they'd stop me.”
- “We had to stop messing around because checkout collapsed.”
- **“Can we do another round?”**

Do not optimize simply for maximum destruction. One missing cart that generates meaningful interaction is more valuable than hundreds of irrelevant exploding objects.
